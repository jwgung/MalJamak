# 작업 기록 (2026-10-12 ~ 10-13)

다음 작업자가 이어받을 수 있게 하루 동안의 결정, 검증 결과, 남은 과제를 정리한다. 기능 설명과 사용법은 [README](../README.md)에 있다.

## 목적 (사용자 결정)

1. **PC용 범용 STT** — 단축키를 누르고 말하면 포커스된 입력창에 들어간다.
2. **청각장애인용 현장 자막** — 문자통역사가 하던 타이핑을 STT 가 초안으로 대신 쓰고, 조작자가 조각을 검토·수정해 내보내면 프로젝터에 큰 자막으로 뜬다. 교회 설교가 주 사용처.
   - 화면: 같은 PC 화면이나 프로젝터 · 교정: PC 조작자가 직접 · 소리: 현장 마이크(믹서 출력을 PC에 직접 넣을 수도 있음)
   - 자막은 틀릴 수 있지만 사람이 고칠 수 있어야 한다. 문장이 통째로 빠지는 것이 오인식보다 나쁘다.
   - 검토 방식은 자동 내보내기(카운트다운)와 승인 방식 둘 다 설정으로.
3. **개인 자막** — 청각장애인 본인 PC 에서 Zoom·화상회의·온라인 강의 소리를 바로 자막으로 (검토 없음, 지난 자막 다시 보기).
4. **순차통역 현장** — 강사(원어)와 통역사가 번갈아 말할 때 통역 언어만 자막으로. 동시통역은 방송이 통역만 내보내므로 일반 방식으로 충분.

## 사용자가 내린 결정 (다시 묻지 말 것)

- 일단 **Windows 기준**으로 만든다. Mac·Linux 는 되면 좋음.
- 줄바꿈은 기계 추측 대신 **조작자 `Shift+Enter`** (메신저 관례). 자동 줄바꿈은 실험 옵션으로만, 한국어 전용.
- 빠진 통역은 **조작자가 알아채고 기계가 번역을 돕는다** (원어 줄 클릭 → 번역 제안). 자동 누락 감지는 시도 후 제외.
- 언어는 제한하지 않는다(22개 목록). 한국어 규칙(어미 자르기·자동 줄바꿈)은 한국어일 때만, 다른 언어는 `Shift+Enter`.
- **단어장 기능은 뺀다.** Groq 키는 가려서 보여 준다.
- 선택지가 적은 설정도 **드롭다운 그대로** 둔다(버튼형으로 바꾸지 않음). 버튼·입력칸 높이는 통일.
- 자막 화면에는 **전체 화면 버튼**을 따로 둔다.

## 핵심 설계 결정과 근거

- **엔진 = 숨긴(headless) Chrome 의 Web Speech API.** 무료이고 구글 클라우드 품질. Linux 헤드리스 + 가짜 마이크로 동작 확인, Windows CI 에서 설치본 엔진 연결 확인.
- **오디오는 트랙으로 넣는다** (`SpeechRecognition.start(track)`, Chrome 135+). 마이크 선택, 시스템 소리(Python 캡처 → MediaStreamTrackGenerator. Windows 는 PyAudioWPatch WASAPI loopback 을 장치 형식 그대로, macOS·Linux 는 soundcard 16kHz 모노. 프레임마다 8바이트 형식 머리 `server.pack_audio`), 테스트 영상(audio.captureStream) 모두 같은 경로.
- **Groq 은 확정 문장에만.** 교정은 적극적 프롬프트가 보수적보다 나음(단어장은 v0.6.1 에서 사용자 결정으로 제거). 20B/120B 속도 차이 0.1~0.2초라 120B 기본.
- **조각 나누기**: 문장 확정 → 말 멈춤(0.7초) → 어미(~다, ~요, ~고, ~는데 …) → 최대 대기(4초). 내보낸 위치는 단어 수가 아니라 글자 수로 기억(Chrome 이 확정할 때 단어를 합치거나 나눈다).
- **세션이 끊기면 아직 확정 안 된 말까지 조각으로 넘긴다** (네트워크 오류 때 문장 유실 방지).
- **순차통역**: 쉼(0.3초)마다 인식 세션을 새로 열고, 인식기 입력을 0.6초 늦춰 경계를 맞춘다. 연속 세션 + 단발 세션을 겹쳐 돌리고 결과를 `InterpretMerger` 로 합친다(아래 실험 경과).
- **다국어 거르기**: 순차통역 결과는 통역 언어의 글자 체계(한글·라틴·한자/가나·키릴·태국·데바나가리·아랍)로 다른 언어 단어를 뺀다. 강사와 통역이 같은 글자를 쓰면 인식기가 다른 언어를 무시하는 데만 기댄다(미시험).
- **번역 제안·직접 입력 조각**: `kind=suggest` 는 자동 내보내기·모두 내보내기에서 빠지고 조작자가 확인해야 나간다. 조각은 서버 순서대로 제자리에 끼워진다(교정 화면도 같은 순서로 그린다).
- **화면**: 공통 디자인 `voicekb/web/ui.css`(밝게/어둡게, 컨트롤 높이 36px), 공통 언어 목록 `voicekb/web/langs.js`.

## 실험 수치 (같은 설교 영상, 유튜브 자동 자막 대비)

- Chrome 클라우드 인식 1분: 문자 일치율 93.9%, 10분: 90.3%(문장 확정만 쓸 때. 네트워크 오류 3회 동안 문장 유실)
- 같은 3분, 문장 확정만 676자(83.2%) → 조각 방식 825자(93.4%)
- 자르는 지점이 어미인 비율: 2초 고정 37% → 자연스러운 지점 71%, 평균 간격 2.1초 → 2.3초
- 오프라인(기기 내) 인식: 실제 PC 의 일반 Chrome 에서는 동작(기본 마이크·트랙 둘 다). 정확도는 클라우드보다 확실히 낮음. Linux 헤드리스·Windows CI 에서는 "Unable to find SODA files" 로 실패 → **우리 앱(헤드리스)에서 PC 동작 미확인**
- 참고 기준: Ofcom 라이브 자막 지연 권고 최대 3초(2023 제안 평균 4.5초), 실제 방송 평균 5.6초, 정확도 98%. 지금 기본값(조각 ~2.3초 + 카운트다운 3초)은 약 5초.

## PC에서 아직 확인 안 된 것

- 트레이 아이콘·전역 단축키·실제 붙여넣기, 현장 자막 기본 흐름은 사용자가 동작 확인함. 그 외:
- 현장 자막을 실제 마이크·믹서 입력으로, 자막 화면을 프로젝터 전체 화면으로(새 전체 화면 버튼 포함)
- 순차통역을 실제 교회 현장 소리로 — 현장 쉼의 소리 크기에 따라 기준값(RMS 0.02) 조정이 필요할 수 있다
- v0.5~0.6 새 화면(교정 ⚙ 패널·설정 탭·드롭다운 모양)을 Windows Chrome 에서
- 한국어 → 영어 등 번역할 언어를 바꾼 PC 소리 자막의 실제 품질, 같은 글자 체계 언어 쌍의 순차통역
- PC 소리 자막 창(tkinter)의 휠 스크롤·표시·v0.5 글꼴/색/마우스 올림 안내 — 이 서버엔 tkinter 가 없어 미실행
- 설치 파일 군살 빼기 후 Windows 시스템 소리 캡처(`soundcard` → `PyAudioWPatch` WASAPI loopback, 장치 형식 그대로 보내고 엔진이 리샘플) — 이 서버에선 가짜 pyaudiowpatch 로 48kHz 스테레오·무음 채우기까지만 확인
- 번역 모델 받기 창에서 끝까지 받아지는지, 받은 뒤 내장 번역으로 자막이 나오는지
- v0.7 조작자 키: Windows 에서 `Ctrl+Space` 가 한/영·입력기 전환과 겹치는지(겹치면 다른 키로), ⏸ 멈춤 중 카운트다운이 멈췄다가 다시 흐를 때 새로 시작되는지
- v0.7.2 교정 화면(어두운 테마, 지금 조각만 크게)이 실제 현장 속도에서 한눈에 들어오는지, 강사 원어 칸 손잡이 끌기
- 오프라인 인식이 헤드리스 엔진에서 되는지 (안 되면 이유를 띄우고 멈추게 해 둠)
- macOS·Linux 데스크톱 전반 (코드상 지원, 실기 미검증)

## 순차통역 모드 (v0.4.0) — 실험 경과

시험 자료: 팀 딜레나 목사 설교 한국어 순차통역 영상(youtube 74mKr5o2gyM) 3:00~5:00. 기준은 유튜브 한국어 자동 자막(통역 구간만 담김).

| 단계 | 일치율 |
|---|---|
| 한국어 인식기 하나 그대로 | 거의 0 — 한 세션에 두 언어가 섞이면 한국어 인식기가 앞 몇 단어 뒤 멈춘다 |
| 쉼(0.3초, RMS<0.02)마다 새 세션 | 64% |
| + 인식기 입력 0.6초 지연, 이전 세션 1.2초 겹쳐 돌리기, 후처리 | 71~74% |
| + 단발 세션 병행으로 빈 곳 메우기 + 비슷한 중복 합치기 | 77~79% (실험 페이지) |
| **앱 전체 (전용 쉼 값 분리 + 합치기 수정 후)** | **81~84%** |

- 바통 넘김 쉼은 0.3~1.0초(영상 분석). 일반 모드 조각용 `pause_ms`(0.7초)와 이름이 겹쳐 처음엔 35%가 나왔다 → `interp_*` 값으로 분리.
- 각 인식기는 다른 언어를 대체로 무시한다(한국어 인식기는 영어에 대부분 무응답). 그래서 "한국어만 받기"가 자연스럽게 된다.
- `stop()` 하면 처리 중인 마지막 단어가 버려진다 → 바로 끄지 말고 겹쳐 돌린 뒤 끈다.
- 합치기(`InterpretMerger`)는 앞부분 반복 떼기 + 공통 구간이 걸친 최근 글 구간과의 유사도(≥0.75)로 중복 판정. 사례는 `tests/interpret.test.mjs`.
- 남은 문제: 영어 음차("파워포", "엑세스 15")가 가끔 섞임, 통역 20% 안팎 유실(조작자가 원어 참고 줄로 보완).
- **누락 자동 감지는 시도했지만 뺐다** (v0.4.1 작업 중): 쉼 구간마다 ko·en 결과 유무로 "말소리는 있는데 결과 없는 구간"을 찾으려 했으나 0건.
  원인 ① 원어 인식기가 한국어 구간에서도 영어를 지어냄("Tumblr local Bingo" 0.78, "come back Wednesday Hometown now" 0.97 — 신뢰도로 완전히 못 거름)
  ② 통역이 일부만 빠지면 나머지 한국어가 나와 "통역됨"으로 보임. → 빠진 걸 알아채는 건 조작자, 번역은 기계(원어 줄 클릭 → 번역 제안)로 결정.
- 진단: CDP 로 엔진 페이지에 `window.VK_DEBUG = true` 를 주면 세션 열림·원본 결과·소리 크기가 console 에 찍힌다.
- 동시통역은 방송에서 원어를 끄고 통역만 내보내므로 일반 방식으로 충분(사용자 판단).

## 개발·검증 방법 (이 서버 기준)

이 서버는 SSH 전용이라 화면·사운드카드가 없다. 헤드리스 Chrome·가짜 마이크·PipeWire 가상 스피커·CDP 로 대부분을 검증했고,
그때 쓴 스크립트와 방법은 [`tools/dev/README.md`](../tools/dev/README.md) 에 있다 (가짜 Groq, 화면 캡처, 엔진 진단, 순차통역 채점).

- **단위 테스트**: `node tests/chunker.test.mjs`, `node tests/interpret.test.mjs`, `python -m unittest discover tests` (CI 에서도 실행).

- 실험 브랜치 `exp/on-device-speech`: 오프라인 인식·Groq 교정 비교용 테스트 페이지(`experiments/ondevice/test.html`).
